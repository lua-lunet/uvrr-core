The schedule is computed, not configured. A constructive solver --- Rust code embedded in the engine, as in the demonstration of Section~\ref{sec:demo} --- answers the demand: get from configuration $A$ to configuration $B$ without a violation of the rules. Given the serving configuration and the target, concretely the crashed identity evicted and the fresh identity seated, the solver emits the series of operations that takes one into the other: joins and leaves at weight zero, unit increments and decrements, and exact doubling and halving~\cite{votingweights}. Each emitted batch changes at most one unit of total absolute weight or scales every weight exactly, so every intermediate era satisfies the intersections~\eqref{eq:same}--\eqref{eq:adjacent} on its own (Section~\ref{sec:method}). For a response set $R$ that is a strict majority at both endpoints, writing $M_w(R) = \sum_{n \in R} w(n)$ and $T(w) = \sum_n w(n)$, the construction keeps the margin \begin{equation*} \mu_w(R) = 2 M_w(R) - T(w) > 0 \end{equation*} at every row: the edits move only towards their targets, so the margin never falls below the strictly positive final margin, each unit edit preserves the cross-era intersection, exact scaling preserves the quorum families, and zero-weight membership edits touch neither. The plan the solver emits is its own certificate, the invariants verified against every boundary before a single message is sent: a formal proof assistant embedded in the running system, and no prior system does this. Plans arrive on the leader's dedicated admin ingress, which the host polls before the regular client queue at every selection, so a reincarnation request never waits behind client traffic. A step the gates refuse, because the cluster changed underneath the plan, aborts the execution and the operator re-plans from the configuration that committed; a leader dying mid-sequence leaves only safe eras that a new leader can continue (Section~\ref{sec:results}).
